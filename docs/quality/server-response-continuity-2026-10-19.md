# Preserve failed-body diagnostics and last-good Feed responses

Local source candidate; not production acceptance.

The completed hosting-recovery check reported “Server feed schema is not supported” during a fresh signed-in Feed refresh. The actual failed response body is unavailable, so its precise cause remains unverified. Source inspection found a separate reproducible fault: the shared sync client converted every JSON-body failure into `{}` even after HTTP 200. Feed loading could cache that empty response and its ETag, then report a schema error. A body cancelled by the existing whole-response deadline was also swallowed.

The shared client now rejects unreadable successful responses with a fixed `server_response_invalid` message. Cancellation reaches the existing timeout/caller cancellation handling. A non-JSON HTTP error page retains the existing HTTP/auth error path. Failed bodies never reach the existing response-cache callback. No automatic retry, timeout increase, schema relaxation, account write, sporting fact, source observation, Follow rule, request owner or scheduler is introduced.

The existing `validate-hobby-feed-client.js` regression retains overlapping-request, 304, invalidation, HTTP failure and account-switch controls. New actual-client cases reproduce the original failure, verify last-good payload/ETag preservation after a failed body, preserve non-JSON HTTP 503, and exercise a body abort through the real finite request timer. The expanded gate and affected server-persistence, authenticated-startup and cross-device checks pass on Node 24.21 with external networking blocked. The first new timeout harness incorrectly reused storage already migrated by another client; its failed receipt is retained separately, and an independent stored session corrects the harness without changing application behaviour.
