# Device-only preference recovery

Source candidate only, 29 October 2026. DEPLOY owns integration, generated files, release and the eventual single phone step. This does not prove the affected iPhone is fixed. User accepts recreating unsynced follows; account deletion/server reset is not authorized.

Account → Data & recovery adds a deliberate two-step “Use saved account preferences on this device” action. It explains loss of unsynced preferences. It reads the authenticated account's saved row once through GET `/api/user-state?recovery-snapshot=v1`, skipping the normal GET's reset-recovery RPC. The SDK uses an existing non-expiring session, with no refresh, retry or session persistence. Missing/near-expiry auth refuses. No query/body target user is accepted.

The action binds the confirmed account/session/profile/sync lifetime before deferred loading, checks RAM preferences, persisted profile bytes and accepted baseline throughout, invalidates old sync work and waits for it to settle. Recovery blocks newly queued sync; already-issued requests cannot be unsent. The fresh read happens after settling. An intervening edit refuses.

Only a current, complete, own-account state that roundtrips through the actual preference normalizer and payload without changes can recover. Historical/normalization differences refuse; this action adds no schema/default accommodation. If any unrelated remote root differs from the previously accepted baseline, recovery refuses before committing, avoiding remote additions being interpreted as local removals. Genuine pending local actions remain intact.

Success writes and reads back one `ns_profile_v1:<activeProfileId>` record. It replaces only preferences/domainPreferences/competitionPreferences/entityFollows/viewingPreference/learningPreference, removes only the exact captured owner's receipt, and preserves all other bundle fields and receipt owners. Full preferenceGraph remains in preferences as well as its existing split sections so reopening cannot borrow the old graph. No profile/install pointer, legacy mirror, auth key, pin queue, rating, action, spoiler, archive, other profile or server row is changed. Actual profile loading prefers this profile copy over the old legacy preference mirror.

RAM preferences and accepted baseline are updated only after verified commit. The baseline is the actual fresh server response, never an ACK or manufactured prior receipt baseline. The success message requires a normal Sync now check; recovery does not claim all data is synced. No recovery PUT, reset RPC, receipt replay, broad applyServerState/savePreferences or automatic save is called.

Storage failure handling: a failed write leaves RAM unchanged. A transient failed readback rolls back only after rereading and proving ownership of this operation's exact bytes. A different/newer record is never overwritten. If ownership or rollback cannot be verified because storage is unavailable, the outcome is explicitly uncertain: retain original RAM/preferences/receipt and pause sync. Durable restoration cannot be guaranteed in that case. Keep the app open; do not present this as successful recovery or advise reload/clear/reinstall.

Proof: `node scripts/validate-local-preference-recovery.js` uses disposable storage, constructed sessions, actual index recovery/normalizer/payload/reconcile/writer/planner/CAS/ACK/profile reopening, and API/SDK/UI doubles. Existing harness taxonomy/UI/service adapters remain doubles; this is source proof. It exercises the pre-recovery hold, immediate no-PUT sync, later deliberate edit/ACK, remote OFF/empty/removal choices, pending actions, foreign receipts, async account/session/profile/generation/local edit fences, stale/incomplete response, unrelated remote changes, write/readback uncertainty, one GET/no refresh/no retry and normal GET compatibility. No browser/native/network/customer operation is performed.

Shared release dependencies: index.html, config/server-sync.js, config/profile-storage.js, deferred config/preference-reset-ui.js and api/user-state.js. The new helper config/local-preference-recovery.js must be served, and deferred UI caching must be accounted for. DEPLOY must allocate current UI599 integration, version/cache/generated/runtime budget checks and hosted acceptance. No migrations, new environment variables, refresh/scheduler changes or production data operations are needed. Comprehensive export checkpoint 6ee8950 and frozen PR94/98 are excluded.

Rollback: DEPLOY reverts this source candidate and its generated release outputs through its normal release lane. Successful deliberate local preference discard cannot be reconstructed from this feature; saved server data is untouched. No automatic local undo is claimed.
